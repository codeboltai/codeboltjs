How the MiniApp system fits together

This repo defines a small MiniApp SDK, a Nitro integration, a local multi-app host, deploy tooling for provider outputs, and experimental cloud routing packages. A MiniApp is authored as a Nitro app with normal UI/API routes plus CodeBolt-specific tool and collection definitions.

SDK: @codebolt/miniapp Host: @codebolt/miniapp-host Deploy CLI: @codebolt/miniappmanager Router Worker: @codebolt/miniapp-router-worker

Repo Map

The repo is a pnpm workspace with package code, runnable examples, compatibility gates, and node tests.

Authoring Contract

A MiniApp is a Nitro app with a small CodeBolt layer. The normal UI and API stay normal Nitro; CodeBolt tools and collections live in predictable folders.

Expected MiniApp source layout

my-miniapp/
  nitro.config.ts
  public/              # static UI, or Vite output copied here
  server/
    api/               # normal MiniApp HTTP API
    routes/            # normal Nitro routes
    tools/             # default exports from defineTool()
    collections/       # default exports from defineCollection()

React/Vite variant

examples/lead-react/
  src/                 # React source
  vite.config.ts       # builds into public/
  server/api/          # standalone HTTP API
  server/tools/        # CodeBolt tool definitions
  server/collections/  # collection schemas
Current contract: one UI entry in the manifest, controlled by codeboltMiniApp({ title, route }). There is no active defineView() or server/views contract in this checkout.

Nitro Module Flow

@codebolt/miniapp/nitro owns discovery, generated tool wiring, validators, target resolution, and manifest emission.

resolveTarget()

Maps MINIAPP_TARGET to Nitro presets: local standard output, Vercel, Netlify, Deno Deploy, node-server, and Cloudflare module.

codeboltMiniApp()

Registers the CodeBolt build/runtime additions. It does not replace Nitro routing; it extends Nitro with MiniApp discovery and host metadata.

Generated manifest

The host and manager use this as the source of truth for ID, title, tool list, collection schemas, static assets, and built runtime paths.

Local Host Runtime

@codebolt/miniapp-host runs many built MiniApps behind one Node HTTP server. Each MiniApp gets a localhost subdomain and a lazy worker runtime.

  • Discovery: the host reads <miniappDir>/<child>/.output/codebolt/miniapp.manifest.json for every built child app, or explicit appRoots.
  • Routing: lead-react.localhost maps to manifest ID lead-react. Static paths are served directly; backend paths forward to the MiniApp worker.
  • Isolation: each MiniApp runtime is a Node worker thread importing that app's built Nitro handler.
  • Capabilities: useMiniApp() calls db.*, blob.*, and tasks.* through the injected bridge, not through browser-visible APIs.

Remote Hosting and Manager

@codebolt/miniappmanager builds provider-specific Nitro output and deploys it to Vercel, Netlify, or Deno Deploy.

Vercel

Uses vercel deploy --prebuilt --yes. The manager materializes linked function directories before deploy so Windows junctions do not break uploaded Build Output API functions.

Netlify

Builds a file/function plan, packages functions as zip payloads, adds a fallback redirect, and polls deploy state.

Deno Deploy

Uses Deno Subhosting v2 token shape, creates or reuses the app based on the MiniApp manifest ID, and sends assets plus runtime config.

Packages

Each package has a clear ownership boundary. The SDK/Nitro package is for authoring and build-time wiring; host/router/cloud packages provide runtime environments.

Package Public role Main files What it owns
packages/miniapp SDK plus Nitro integration src/index.ts, src/nitro.ts, src/runtime/tool-handler.ts defineTool(), defineCollection(), useMiniApp(), resolveTarget(), codeboltMiniApp(), tool route handling, manifest emission.
packages/host Local multi-MiniApp host src/index.mjs, miniapp-runtime.mjs, worker-transport.mjs, capabilities.mjs Manifest discovery, localhost subdomain routing, static file serving, worker lifecycle, local capability storage, status and reload routes.
packages/miniappmanager Build/deploy CLI src/cli.mjs, src/index.mjs Provider target builds, dry-run plans, credential resolution, Vercel/Netlify/Deno deploy flows, provider project/app/site derivation from the MiniApp manifest.
packages/miniapp-router-worker Cloudflare Worker install router src/index.mjs, wrangler.jsonc Root-domain app catalog, install records, auth start/callback/logout, subdomain install routing, upstream proxying, execution token forwarding.
packages/sample-cloud Sample capability cloud src/core.mjs, src/index.mjs, src/worker.mjs Development token creation and remote /capabilities/:name implementation for db, blob, and tasks. Can run as Node server or Worker.

Examples and Gates

The examples demonstrate authoring shapes. The gates and tests prove mountability, worker transport, target builds, and remote capability behavior.

examples/leads

Plain Nitro MiniApp with public HTML, multiple API routes, tool definitions, and lead/task collections. It is intentionally broader for testing behavior.

examples/lead-react

Minimal React + Vite example. Vite builds the UI, Nitro packages the server, and CodeBolt still discovers tools/collections.

examples/onboarding

Second domain example with employees and onboarding tool flows.

gates/

Small focused verification apps for mountable output and worker transport. They should stay as compatibility gates while those runtime assumptions matter.

tests/

Node test suite covering capabilities, integration host behavior, router worker behavior, sample cloud, and remote target output.

Important Commands

These are the practical entry points from the root package.json.

Command What it does
pnpm build:examples Builds examples/leads, examples/lead-react, and examples/onboarding.
pnpm start Runs packages/host/src/cli.mjs --dir examples. The examples folder is command configuration, not a hardcoded host dependency.
pnpm miniapp deploy examples/lead-react --target vercel --prod Builds the MiniApp with the Vercel preset and deploys prebuilt output using @codebolt/miniappmanager.
pnpm gates Runs mountable-output and worker-transport compatibility gates.
pnpm test Runs gates, example builds, capability tests, router/cloud tests, integration tests, and remote node/cloudflare target checks.

Boundaries and Current Caveats

These boundaries are important when adding features or examples.

  • Normal app routes: /api/*, /server/routes, and static files belong to the MiniApp. They should work like normal Nitro routes.
  • Host/control routes: /__codebolt/tools/*, /__codebolt/status, and /__codebolt/apps/:id/reload are platform routes. Browser UI should not depend on them as normal product APIs.
  • useMiniApp() needs runtime context: it works inside CodeBolt-hosted tool/API execution where the bridge or remote headers exist. Plain public provider pages should use normal HTTP APIs unless they are called through the CodeBolt router/capability path.
  • Manifest is the contract: host discovery and deployment naming should come from .output/codebolt/miniapp.manifest.json, especially the id.
  • Cloud deployment is split: provider hosting serves the MiniApp runtime; router worker owns install/auth/subdomain routing; sample-cloud demonstrates remote capabilities.
  • Cloudflare constraints: validator code is generated at build time because runtime code generation is not suitable for Worker-like environments.
If a new example is meant to be publicly reachable on Vercel/Netlify/Deno without the CodeBolt router, do not put useMiniApp(event) in routes that are loaded directly by the browser. Reserve MiniApp capability calls for CodeBolt-hosted execution paths.
